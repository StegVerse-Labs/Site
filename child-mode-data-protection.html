Child Mode — Device Data Authority Boundary

Present boundary: Child Mode protects device and account data from optional harvesting by default. A child interaction is not accepted as sufficient authority for optional collection, profiling, advertising, cross-service tracking, or unrelated reuse.

Core rule

CHILD_MODE → OPTIONAL_DATA_HARVESTING = DENY_BY_DEFAULT → CONSENT_DEPENDENT_COLLECTION requires legally authorized consent path → guardian/authorized adult approval is PURPOSE_SCOPED → approval for one purpose does not authorize unrelated collection → all collection decisions produce an inspectable receipt

This rule is deliberately stricter than simply displaying a consent popup to a child. If the applicable law requires parental or guardian authorization, the child cannot create that authority by tapping “Allow.” Where a jurisdiction permits a sufficiently mature child or older teen to consent for a particular processing purpose, Child Mode may still impose the stricter StegVerse default and require an authorized adult for optional harvesting.

Purpose-scoping rule: guardian consent only authorizes the exact scoped purpose; it does not create blanket permission for unrelated collection, retention, profiling, disclosure, or reuse.

Consent and authority

Child Mode does not encode the claim that every person under 18 is legally incapable of every form of consent. The legal age and capacity for valid consent are jurisdiction- and context-dependent. Child Mode therefore encodes a stronger product rule:

CHILD OR PROTECTED-AGE ACCOUNT → child tap/click alone does not authorize optional harvesting → determine jurisdiction + age/capacity rule → determine whether consent is legally available and who may give it → require guardian/account-holder authorization when policy or law requires → bind authorization to exact data + exact purpose + exact recipient + retention window → deny everything outside that scope

Operational delivery

Child-dedicated device: the data boundary can be hard-bound at the OS, managed-device, secure-storage, or trusted policy layer.

Shared device: an age-governed child account activates the protected data boundary automatically; switching to an adult account requires authenticated account transition.

Guardian-controlled temporary Child Mode: entering or exiting the protected state requires fresh account-holder reauthentication. Exiting does not retroactively grant access to data collected while Child Mode was active because optional harvesting should not have occurred.

Law comparison

United States: COPPA generally requires verifiable parental consent before covered operators collect, use, or disclose personal information from children under 13, subject to limited exceptions.

United Kingdom: when consent is the lawful basis for an information-society service, children 13+ can generally consent for themselves; below 13, parental-responsibility authorization is generally required. Child Mode may impose a stricter product default.

Australia: privacy law does not set one universal consent age; capacity is assessed, with age and maturity relevant. Child Mode therefore treats optional harvesting as unavailable unless an authorized policy path establishes valid authority.

2026-08-07 — Device-data harvesting boundary

Change: Child Mode now explicitly denies optional device-data harvesting by default and rejects child UI interaction as sufficient authority for consent-dependent harvesting.

Rationale: child safety must protect not only social interaction capabilities but also the device data plane. Permission to use a device or participate in a network must not silently become permission to harvest the device.
