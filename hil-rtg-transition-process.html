Response submission as an event-induced transition topology

The response receiver is not required to remain alive. The participant action induces the short-lived Transition Elements needed to validate, transfer, commit, receipt, notify, and then expire.

Core transition geometry

Site page opened
  → local preparation element exists
  → no response bytes leave the participant device

Response PDF attached
  → attachment-candidate element
  → local type, size, and PDF-signature checks
  → local SHA-256 calculation
  → provenance candidate assembled
  → optional notification email remains local unless explicitly enabled

Upload committed
  → attempt identifier assigned
  → admissibility and intake lease requested
  → ephemeral ingress element instantiated
  → packet transferred across the StegVerse submission boundary
  → canonical primary, prompt, response, and provenance chain checked
  → durable custody commit attempted
  → receipt or refusal/failure record emitted
  → notification addressed to Rigel@stegverse.org
  → optional privacy-minimized copy queued for the participant
  → continuity checkpoint written when required
  → ephemeral elements expire

Why the action induces the runtime

The transition does not justify an idle receiver. It justifies a stable, wakeable initiation address. The participant's commit action supplies the event that creates the minimum topology needed for that one attempted state change. Compute lifetime should remain proportional to the transition lifetime.

Stable before execution

Site route, service identity, canonical hashes, policy references, transition schema, required notification destination, and an addressable wake mechanism.

Ephemeral during execution

Upload lease, ingress handler, temporary authority, buffers, validators, signing context, queue workers, temporary files, and restricted delivery context.

Durable after execution

Only custody, evidence, result, notification, retry, reconciliation, and reconstruction state required by the outcome. A participant address persists only as long as required by the governed delivery and retention rule.

State changes recorded per attempted submit

ATTEMPT_CREATED
Attempt ID, originating Site contract version, timestamp, and local-preparation declaration. No response bytes are required at this stage.
PACKET_TRANSFER_STARTED
Attempt ID, expected response hash when available, lease or capability reference, and transfer start time.
PACKET_RECEIVED
Submitted-file hash, byte count, provenance-manifest hash, and temporary custody state.
CHAIN_VALIDATED or CHAIN_REFUSED
Canonical primary hash, prompt hash, response hash, applicable policy hash, validation result, and bounded reason codes.
CUSTODY_COMMITTED or CUSTODY_FAILED
Durable pointer or custody reference, commit timestamp, cleanup result, retry eligibility, and last completed transition.
RECEIPT_EMITTED
Submission ID, receipt ID, chain-validation state, receipt hash, signature, review state, and publication state.
NOTIFICATION_RECORDED
A privacy-minimized state-change notification addressed to Rigel@stegverse.org. When the participant explicitly opts in, the same attempt notification is separately queued for their supplied address.
NOTIFICATION_DELIVERY_RECONCILED
Required-recipient and optional-recipient delivery states are recorded independently. Partial or failed email delivery cannot change the accepted, refused, or failed submission outcome.
TRANSITION_ELEMENTS_EXPIRED
Lease revocation, temporary-state cleanup, final continuity head, and unresolved reconciliation state if any.

Success persistence

Persist the submission and receipt identifiers; submitted-file, provenance, primary, prompt, policy, and receipt hashes; custody pointer; authority decision reference; timestamps; chain-validation result; notification record; review/publication state; and continuity-chain head. Process memory, temporary authority, upload buffers, and the executing node expire.

Refusal persistence

Persist the attempt ID, refusal stage, bounded reason code, policy reference, timestamp, retry eligibility, whether bytes were retained, cleanup result, and notification record. Rejected response bytes should not remain unless an explicit quarantine rule admits retention.

Infrastructure-failure persistence

Persist the attempt ID, last completed transition, failure class, available hashes, temporary custody state, retry/reconciliation state, lease expiration, cleanup status, and notification record. A failure after custody commit must resume from custody rather than silently creating a second submission.

Abandonment before commit

Opening the page and attaching a file create local preparation state only. Closing the page before upload commitment requires no server-side submission record. An optional email address entered before commitment remains local and may expire with the page.

Optional continuity components

Ecosystem Chat Node

May reconstruct and execute the transition topology, but is not the sole permissible runtime and is not required for basic intake.

KnowledgeVault

May preserve research meaning, objectives, adjudication, and publication context. It should not receive participant data beyond the governed response-submission contract.

Continuity Vault Kit

May preserve transition heads, unresolved work, replay inputs, and reconstruction instructions. It is a continuity method, not a mandatory transport host.

Boundary rule: these optional components strengthen reconstruction and controlled continuation but do not expand collection authority. Zero user data crosses the StegVerse boundary outside of the response packet, its participant-authorized metadata, the optional attempt-notification address, and the minimum evidence required to validate, receipt, and notify that submission.

Notification contract

Every committed upload attempt must produce one attempt-level notification addressed to Rigel@stegverse.org. The participant may explicitly request a copy by supplying an email address. That address authorizes delivery of this attempt notification only; it does not grant publication consent, attribution authority, marketing permission, account creation, or broader contact authority.

The privacy-minimized notification artifact and receiver receipt must not expose the participant address. The address belongs only in a restricted delivery envelope. Notification delivery failure must not rewrite an accepted submission as refused; it creates a separately recoverable delivery state.

Excluded from receipt and public notification artifact

  response PDF contents
  prompt or response prose
