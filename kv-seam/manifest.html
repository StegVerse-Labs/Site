The manifest

A submission to the seam is not an upload. It is a manifest — one file that describes the work precisely: who is submitting, where results go back to, which files are involved and where they sit, and the protocol — exactly what is to be done with them. The submission describes itself; there is no separate form and no account to create. Sending the manifest is the work order.

The scaffold — copy it, fill it in, send it

SUBMITTER: <your identity>
RETURN ADDRESS: <in your own storage — where the return is sent>
PARTICIPATION CLASS: external / native
FILES:
  - name: <file name>
    locator: <where it sits in your storage>
    sha256: <the file's SHA-256 digest>
PROTOCOL: <what you want done, precisely — including the return form you want>
RETURN: <chat / file at the return address>

The full instruction file — the steps and the rules as well — is the submission kit: download the submission kit.

The fields

Submitter is who is asking — the identity the return is owed to. Return address is a place in your own storage; results are delivered there, never held at the seam. Participation class is external (arriving from outside the ecosystem) or native (you hold a registered, healthy node — step 1 on the seam page). Files lists each file by name, by the locator where it sits in your storage, and by its SHA-256 digest. Protocol is the heart of it: what you want done, stated precisely — the operation, the constraints that govern it, and the form you want the results in. Return says how the governed return reaches you.

The fingerprints

Your files never travel. They are checked where they sit, against the digests in your manifest — that is what the SHA-256 fingerprint is for. If the bytes at a locator do not match the digest, the disposition is a mismatch, not an arrival: nothing is processed on the strength of a file that is not the file you manifested.

Your intent decides the stages

The manifest is read — in the sandbox, by the manifest logic — and the reading derives how many stages your submission has. State that a data packet needs governing, and the derived set is a single stage: EXECUTE. State that you intend to compare systems, and the derived set is the staged pipeline — PROPOSAL, an evaluation of the test's intent against the ecosystem's purpose, FINAL REVIEW, FREEZE, EXECUTE — four submissions, each a governed decision, because collapsing a stage would delete a decision someone is entitled to make. The stages are never picked from a menu and never taken on trust from labels; they are computed from what your manifest says and what your packet contains.

Examples

Example A — govern a packet (one stage)

SUBMITTER: A founder testing governance
RETURN ADDRESS: the founder's own storage
PARTICIPATION CLASS: external
FILES:
  - name: diagnostic-packet.json
    locator: founder storage / tests
    sha256: 17db506b… (the packet's digest)
PROTOCOL: Govern this data packet against the constraints
  stated in it; disposition each transition individually;
  return the results as a JSON file.
RETURN: file at the return address

The reading derives [EXECUTE] — govern it and return the results. The return is the per-transition dispositions in JSON, the receipt declared at the top.

Example B — compare two systems (staged)

SUBMITTER: Two founders, by agreement
RETURN ADDRESS: each founder's own storage
PARTICIPATION CLASS: external
FILES:
  - name: shared-record-set (frozen)
    locator: as agreed by the parties
    sha256: the frozen set's digest
PROTOCOL: Evaluate this data set for the purpose of
  comparing two governance systems against the same record.
RETURN: file at each return address

The reading derives [PROPOSAL, EVALUATION, FINAL REVIEW, FREEZE, EXECUTE]: the proposal is submission one; the sandbox evaluation weighs the test's intent against the ecosystem's purpose; agreed final review is submission two; freeze, submission three; execute, submission four — the minimum four submissions of the staged form.
