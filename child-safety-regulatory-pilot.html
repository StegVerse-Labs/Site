Child Safety Regulatory Pilot

Purpose: provide a public, regulator-testable way to compare blanket minimum-age account restrictions with deterministic Child Mode governance.

This is not a self-exemption from a ban. Protected users enter a pilot only under an explicit lawful pilot/sandbox/authorization path defined by the relevant authority. Otherwise the ordinary minimum-age rule continues to apply.

Current enforcement problem

A ban can be legally clear while still requiring evidence that platforms actually detect protected users, prevent new accounts, resist bypasses, correct errors, and avoid turning age assurance into a new data-harvesting channel.

BAN ENFORCEMENT → age assurance → detect existing underage accounts → prevent new underage accounts → prevent workarounds → review/appeal errors → regulator monitoring → enforcement when evidence supports breach

Pilot admission

REGULATOR / LAWFUL PILOT AUTHORITY + defined jurisdiction + defined protected age cohort + defined service/capability perimeter + defined duration / termination condition + approved age-assurance method + approved evidence schedule → PILOT_ADMISSIBLE

Zero harvesting is the starting point

OPTIONAL_DATA_HARVESTING = DENY_BY_DEFAULT

Admission to the protected environment does not authorize optional extraction of the child's device or behavioral data. Child Mode treats interaction authority and data authority separately.

Default DENY

Contacts, files/photos, precise/background location, clipboard, advertising IDs, cross-app/service IDs, behavioral profiles, inferred interests, nonessential telemetry, and microphone/camera-derived data beyond a bounded foreground function.

Any exception must be scoped

Exact data class + exact purpose + exact recipient + retention window + lawful authority reference + receipt. Guardian authorization cannot become blanket permission.

Five-layer evidence package

1. Eligibility

Age-assurance result, jurisdiction, age band, policy version, appeal state, evidence-retention status.

2. Capability denials

Reproducible regulator test accounts and deterministic ALLOW/DENY results.

3. Data egress

Requested class, purpose, recipient, authority, decision, released bytes/records, retention, receipt hash.

4. Boundary history

Newest-first public record of every threshold/capability/data-rule change with rationale and implementation version.

5. Outcomes/incidents

Privacy-preserving aggregate metrics for bypass attempts, appeals, denied transitions, allowed positive interactions, data requests, incidents and suspensions.

Fail closed

age assurance unavailable → no new protected-user admission policy/receipt chain broken → sensitive transition DENY unknown data egress detected → affected data class DENY + incident mandatory boundary test fails → affected pilot access SUSPENDED regulator termination condition → pilot disabled

Why this changes the policy question

The current minimum-age approach treats the covered social network as the regulated risk surface and requires the platform to keep protected users out. This pilot tests whether government can instead require the platform to prove, continuously and independently, that the dangerous interaction and data authorities do not exist for the protected user.

The goal is not to shift blame away from platforms. It is to make platform responsibility more granular and more observable: prove what the system cannot do, prove what data it cannot take, and prove what happens when those boundaries fail.
